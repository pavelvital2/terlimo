## Исправление

- PurchaseAttempts format2 различает quote-only и unresolved create. Перед native.trySend явного Pay атомарно сохраняются account_ref из принятого /me, точный принятый quote event, полная selection и первоначальные quote/payment keys. Принятый payment ID/receipt и outcome записываются до публикации UI. Используется существующий encrypted AtomicFile; grants/account state не выводятся из purchase journal.
- В journal сохраняются оригинальные принятые bridge events; восстановление использует тот же PaymentsContract parser. Новый DTO/wire/backend не вводился. Поднята старая локальная граница purchase record16KB до существующего общего encrypted-state бюджета900KB без увеличения общего бюджета. Полный список slots сохраняется без усечения; ошибка записи до Pay предотвращает отправку, ошибка receipt-записи оставляет исходный Q/K.
- Холодный UI показывает только общий признак незавершённой оплаты. Детали читаются в UI после принятого /me того же account_ref. Другой/непроверенный аккаунт не получает quote/payment/checkout details и не может повторить запрос. Ответ покупки сопоставляется с существующим single-flight и аккаунтом отправки; старый ответ после смены аккаунта не сохраняется и не отображается.
- «Восстановить оплату» — явное действие через существующий purchase service gate. Известен ID: payment_get; неизвестен результат create: payment_create с прежними Q/K, без проверки offer expiry на клиенте и без генерации ключей. Операция восстановления не вооружает create/browser acknowledgement. Startup/render сами Pay/браузер не запускают. Для pending заказа остаётся отдельное явное «Продолжить оплату».
- Пока unresolved, beginQuote/bindQuote/beginPayment/restart не стирают первый заказ; UI блокирует новый выбор/Pay. Ошибки/expired/conflict не превращаются в новый order. Teardown снимает только sending, сохраняя journal; повтор того же Q/K доступен после нового явно начатого восстановления.
- Paid/needs_review переживает restart. Fresh-/me flags не сохраняются: оплаченный заказ требует прежнего совпадения credited revision/actual period/capacity и свежих plans. Needs_review не подтверждается. Лишь terminal receipt либо paid+fresh rights переводят durable outcome в terminal/confirmed и разрешают сознательную следующую покупку. Если запись confirmed не удалась, UI возвращается в ожидание нового подтверждения, barrier остаётся.
- Новый format2 quote-only (Pay не нажимали) сохраняет обычную смену выбора. Immutable displayed offer и повторная проверка явного Pay сохранены; суммы/периоды/права клиент не вычисляет.

## Граница существующего API / старого состояния

В текущем server/terlimo_backend/s5_payments.py create: сначала authenticated installation-bound quote lookup, затем durable payment_orders lookup по installation+idempotency key, и лишь при отсутствии заказа — отказ по expiry (строки примерно210–250). Нормальный unknown-response retry использует эту существующую семантику; новый endpoint для format2 не нужен.

До этой правки старый bound-quote record вообще не содержал Pay-intent, account_ref и receipt. Нельзя доказать, что это quote-only, либо угадать владельца после upgrade. Такой legacy record НЕ replay/rotate автоматически: общий статус «требуется проверка поддержки», без деталей. Это честное ограничение восстановления уже утраченной информации, не заявленный успешный upgrade recovery.

Также неизвестный order не может быть разрешён клиентом, если старый quote удалён, merchant method выключен либо сервер возвращает неразрешающий отказ до возврата durable order. Journal остаётся unresolved, UI сообщает, что восстановить пока не удалось. Для автоматического разрешения таких случаев/legacy нужен согласованный server delta: аутентифицированная read-only reconciliation по исходным Q/K, проверка installation И checkout owner account, возврат существующего receipt/terminal отсутствия заказа без provider create и без зависимости от текущего expiry/merchant availability. Решение об этой серверной операции остаётся root/Инженеру; её здесь нет. Сам по себе generic 404/transport/expiry не принят за доказанный terminal заказа.
