# Решение root по контракту рефералов — 03.10.2026

Принят как основа реализации аккаунтной атрибуции, кода, trial и отдельного учёта наград. Это SOURCE-контракт, не готовая функция. Payment reservation/finality остаётся отдельным техническим остатком; business-условия владельца не меняются. Исходное предложение Архитектора сохранено ниже с обязательными уточнениями root:

1. Награда пригласившему за paid создаётся при **успешном применении основной оплаченной подписки**, в той же транзакции, что applied_entitlement_id/credited receipt. Succeeded-but-needs-review не выдаёт награду за ещё не активированную подписку. Скидка приглашённого при подтверждённой оплате уже consumed; это другой факт. Trial награда соответствует фактической успешной активации trial через принятый grant/outbox/readback путь, не лишь созданию задания. Повторы не создают новый reward. Это сохраняет рабочие правила владельца и исправляет неоднозначность формулировки §4 ниже.
2. Definitive create no_order допустим только если **тот же Q/K больше не может создать order позднее**. Перед ответом durably terminalize точный quote/attempt под штатной сериализацией (можно существующим expires_at) и commit должен пережить emitted ApiError. Без этого снятие reservation/изменение eligibility позже может воскресить старый запрос. GlobalK/sourceQ/unknown имеют приоритет; HTTP409/GET/timeout сами intent не снимают. Новый client proof строго коррелируется по исходным installation/account/Q/K/flight/diskCAS; инвалидированный flight не очищает журнал, восстановление — новый коррелированный replay того же Q/K.
3. Подтвердить единый реальный lock order всех затронутых writers при реализации. Текущее apply_paid_entitlement сначала берёт order FOR UPDATE, затем paid-account advisory; предложение account→order нельзя просто добавить параллельно этому пути. Либо согласованно изменить затронутые writers, либо сохранить совместимый порядок с доказанной сериализацией. Не держать DB transaction на provider I/O.
4. Для скидочных TEST случаев использовать тариф основной подписки200₽ или выше и fake provider/offline fixtures, не реальные деньги. Существующие TEST10/20₽ quotes/orders не переоценивать. Production price≤100₽ правило не вводится; проверить фактический release tariff перед включением. Cancellation finality доказывается провайдером; UI закрытие/локальная expiry не достаточно для release reservation. Точное техническое решение поручено Архитектору отдельно, прочая реализация не блокируется.
5. Никакой автоматической выдачи10дней уже использовавшему trial и никакой скидки аккаунтам без подтверждённой referral eligibility/history. Own-code GET у зарегистрированного с истёкшим доступом допустим. До переключения production согласовать единственного writer и точную миграцию legacy history; SOURCE/TEST не разрешают сейчас эти production изменения.

Следующее исполнение: после ответа исходных текущих поручений передать единый принятый wire клиенту и серверу, без повторных сообщений занятым исполнителям. Архитектор отдельно проверяет bounded provider finality. Все старые доказательства оплаты/updater/recovery сохраняются.

## Уточнение расчёта скидки и ответственности root

Владелец03.10 уточнил: скидку рассчитывает наш сервер, в Platega передаётся уже конечная сумма (например,200₽→100₽). Никакой provider coupon/API скидок не требуется. Это соответствует выбранной реализации. Root снял с владельца запрос в поддержку: внешнего действия владельца сейчас не ждём, разработка продолжается. Неизвестность окончательности отмены сохранена как узкий технический остаток обработки повторных оплат; её нельзя выдавать за запрет простой скидки, разрешение двойной скидки или подтверждённую provider гарантию.

Для привязки приглашения выявлен конкретный пробел текущей регистрации: repeated unbound registration/link заменяет token, а UUID квитанции не доказывает связь с исходным кандидатом. Нужны keyed opt-in регистрация и полный ответ с account/candidate/registration/K; обычная регистрация без кода сохраняет прежний wire. Дополнение библиотеки и fixtures поручено отдельно, конечный контракт передаётся серверу вместе с готовыми fixtures. Это техническая реализация уже согласованной устойчивой привязки, нового вопроса владельцу нет.

# Рефералы: минимальный контракт реализации

Proposal, не implementation. Base2d823640c3823a678bee5e3d4497925d4ec57f64. Решения владельца из26 и финальных дополнений16 имеют приоритет над историческими абзацами. Старый REFERRAL_RULES повторно не добывался. Новый public backend/identity DB не нужны; текущий authenticated service channel, accounts, payment core и worker сохраняются.

## 1. Зафиксированные правила

Свой постоянный code выдаётся verified Telegram account независимо от paid/trial/expired. Друга можно указать до часа/регистрации; час не награждается. Eligible trial7→10 один раз приглашённому; пригласившему отдельно7 за trial и7/14/30 за первую основную paid1/3/6. Неактивный пригласивший получает WAITING, без новой подписки. Приглашённому10000коп. RUB скидки на первую успешную MAIN покупку1/3/6, бессрочно, без prerequisite trial. Повтор/renewal/addon не дают повторной скидки/вознаграждения. Trial и paid события независимы. Никаких уровней/процентов/вознаграждения предшественникам.

«Подходящий trial» сохраняет existing trial_activation.py:197–264: verified account+binding, отсутствие trial history/active commercial, registration within_hour, channel membership. Меняется длительность при подтверждённой атрибуции, не eligibility и не старые уже выданные trial. Paid скидка от этих trial условий независима.

## 2. Wire через существующий service channel

Везде стандартный request_id/error envelope, Authorization session bearer; мутации с existing Idempotency-Key. Добавить только точные method/path в service_relay.py fixed allowlist и Go accountaccess client/bridge. Не требовать VPN data grant или доступности публичного HTTPS. Account info требует authenticated verified account; revoked/foreign installation не получает чужой code. До регистрации authenticated installation может хранить лишь кандидат, не получить свой code.

Предлагаемый v1:

- `POST /api/mobile/v1/referral/candidate`, `{ "code":"CODE" }`, K. Ответ `{ "candidate": {"id":"uuid","state":"pending","code":"CODE"} }`. Максимум32 ASCII alnum, legacy lookup preserves stored spelling, без произвольных URL/TelegramID. Применить существующую legacy-normalization только на сервере. Unknown→404 REFERRAL_CODE_INVALID; malformed→400 BAD_MESSAGE. Для стирания `DELETE .../candidate` сK, ответstate cleared. Пока нет связанного registration token кандидат можно явно заменить; при binding pending→409 REFERRAL_CANDIDATE_LOCKED. Retry sameK/body возвращает тот же receipt, изменённое body→409 IDEMPOTENCY_CONFLICT.
- Existing `POST /registration/telegram/link` принимает optional `referral_candidate_id`. Без него прежнее поведение. В registration_links сохраняется immutable candidate version/id; candidate installation MUST совпасть. При подтверждении Telegram под account lock: заново resolve inviter/no-self/no-overwrite/eligibility, присвоить invited account; candidate не является account_ref. При semantic reject регистрация всё равно завершается; nested referral result `state: rejected, reason: self|already_attributed|ineligible|invalid`, никакой награды. При storage/transient failure не писать ложный terminal reject, retry той же registration.
- `GET /api/mobile/v1/referral` после свежей аутентификации: `{ "account_ref":"...", "code":"...", "links":{"telegram":"https://t.me/terlimo_vpn_wdtt_bot?start=ref_uCODE","web":"https://terlimo.xyz/?ref=uCODE"}, "attribution":{"state":"none|attached|rejected","receipt_id":null,"reason":null}, "benefits":{"trial_bonus_days":3,"discount":{"currency":"RUB","amount_minor":10000,"state":"eligible|reserved|consumed|ineligible|history_pending"}}, "rewards":{"waiting_days":0,"applied_days":0}, "terms_version":"referral-20261003-v1" }`. Не отдавать inviter TelegramID/имя или историю чужих заказов. Aggregate own rewards не означает бесконечное дерево. Code создаётся при account confirmation/import, GET не генерирует новую identity. Если legacy ownership ещё не reconciled:503 REFERRAL_HISTORY_PENDING retryable, не генерировать конкурирующий code.
- Registration result и /me могут вернуть optional `referral_attribution_receipt_id`; authoritative подробности GET referral. Receipt содержит server account owner+candidate id+terminal result; успешная регистрация не гарантирует успешную атрибуцию. Client очищает pending candidate только после durable terminal receipt, при unknown повторяет originalK/token. Account switch не переносит candidate/receipt на другой account.

Client до сети может сохранить введённый код в небольшой installation-scoped pending записи существующего encrypted store; не менять installation keys и payment journal. Перед созданием Telegram link кандидат обязательно подтверждается сервером и связывается с token. Нельзя очистить его после открытия Telegram. Если Telegram Start уже сохранил legacy inviter, существующая серверная привязка имеет приоритет над новым введённым кодом; это no-overwrite, UI показывает окончательный receipt. Сайт/бот используют те же account rules; автоматический deferred link через установку APK НЕ предлагается.

## 3. Account/legacy ownership без новой identity системы

Canonical accounts.telegram_id UNIQUE (0001), telegram_binding.confirm_registration:297+ уже upsert accounts по verified Telegram identity. Это единственный ключ сопоставления legacy users.telegram_id с новым account. Не доверять присланным клиентом telegram_id/legacy_user_id/code как доказательству владения. Код — lookup inviter, не credential.

Additive migration после фактического latest номер выбирает publisher:
- `accounts.referral_code` nullable UNIQUE; `referred_by_account_id` FK+CHECK notself; `referral_attributed_at`, `referral_terms_version`.
- Маленькая таблица installation candidate + registration_links.referral_candidate_id; version/K/digest и result через существующие operation receipts pattern.
- Одно account benefit-state поле/строка: eligibility-history state, reserved_order_id, consumed_order_id (FK), revision. Это не новая payment ledger; деньги остаются payment_orders/events.
- `referral_rewards`: UNIQUE(invitee_account_id, event_kind trial|first_main_paid), inviter/account FK, source entitlement/order FK, days, state WAITING/APPLIED, target entitlement/base/target/revision. Нужен durable receipt награды, не вычисление по статистике. Existing worker применяет ожидающие reward, новый daemon не нужен.
- Quote/order immutable referral snapshot (jsonb либо extension current product), credit receipt явно сохраняет принятую discount/reward source version.

Перед включением writer нужна адресная protected миграция legacy code+attribution+trial/first-main payment/bonuses по verified Telegram identity. Reuse actual stored code, сохранить first-attribution и уже earned/applied rewards: иначе double reward после cutover. Перенос служебных ownership mapping возможен через existing import staging; не создавать вторую базу identity. Уже известные legacy-only inviters должны иметь mapping в тех же accounts до публикации их code; конфликты code/Telegram owner → review, не новый случайный code и не overwrite. Не читать legacy records на каждом app GET, не выдавать новым/старым аккаунтам eligibility по отсутствию локальной строки без migration watermark. Новым подтверждённо post-cutover аккаунтам код генерируется cryptographic random alnum + UNIQUE retry, постоянен.

Bot/site после enable должны обращаться к этому же authoritative referral writer/receipts или быть явно переведены на него до начислений. Старый award worker не должен параллельно начислять те же импортированные intents. Это prerequisite согласованного будущего cutover, НЕ разрешение текущих production изменений. Нельзя обещать одинаковые правила трёх интерфейсов, реализовав только новый Android backend.

## 4. Цена, резерв и callback

Текущий quote schema0024 требует amount_minor>0; product snapshot0036, s5_payments.py:_quote_view/_with_product иpayments.apply_paid_entitlement хранят коммерческий/credited snapshot. Не менять существующие quote/order amounts или old receipts. Existing product contract2 расширить optional:

`pricing: {base_amount_minor:20000, discount_minor:10000, payable_amount_minor:10000, currency:"RUB", discount_kind:"referral_first_main", terms_version:"referral-20261003-v1"}`.

Top-level amount_minor=payable; period/device selection неизменны. Скидка относится только MAIN component, не стоимости выбранных extra renewals. UI показывает базовую цену, скидку и итог вместе, immutable quote approval; callbacks проверяют именно payable, entitlement выдаёт полный frozen period, не пропорцию цены. Сервер создаёт snapshot, клиент его не конструирует.

Quote — обещание цены на ограниченный срок, не резерв на аккаунт: несколько quotes допустимы. Резерв приобретается атомарно перед вставкой нового order/любым providerPOST, **на account**, не installation. Сначала существующие globalK/sourceQ/replay/unknown проверки, затем account benefit lock и fresh owner eligibility. В одной транзакции order(in_flight)+reserved_order FK+frozen snapshot. После commit единственный provider call. SameK/Q возвращает original receipt даже после expiry/изменения flags/consumed. Другая установка с discountedquote получает409 REFERRAL_DISCOUNT_RESERVED; не создаёт row/provider call и не повышает цену молча. Устаревшая eligibility→409 QUOTE_EXPIRED с отдельным reason referral_quote_changed, не existing expired_quote_no_order автоматически.

**Client durable intent barrier:** новый отказ после persist-before-send обязан иметь доказанный no-order terminal receipt, иначе клиент останется unknown. Для reserved/quote_changed вернуть optional `create_resolution:{kind:"no_order",quote_id:Q,request_idempotency_key:K,reason:"referral_discount_reserved|referral_quote_changed"}` только под существующим install lock после globalK/sourceQ/all in_flight+unknown fences. Go/Kotlin codec сохраняет boundedreason и atomic terminal transition с теми же Q/K/account guards, что existing expired_no_order. HTTP409 сам по себе не основание очистить attempt. Старый клиент без поля держит консервативный unknown; feature negotiation rollout обязателен.

Lock order не инвертировать: наружный payment_install_lock, затем transaction account locks в стабильном порядке, затем benefit/order row locks. Callback/reconcile сначала immutable owner из order, затем те же account/benefit locks до order mutation; не держать DB transaction на внешнем provider call. Доступ через quote/install дополнить account-level unresolved MAIN gate: pending/unknown старые undiscounted invoices должны завершиться до нового discounted order. Иначе первый успешный old invoice может гоняться с новым discount invoice. Ранее выданный undiscounted invoice оплачивается по старой цене и receipt без перерасчёта; его успех обновляет first-main history, eligibility не появляется повторно.

Успешный matching callback/reconcile атомарно отмечает account benefit CONSUMED и usual payment succeeded/credit. Повтор не расходует/не начисляет второй раз. Если credited needs_review, paid benefit всё равно уже consumed: факт оплаты не отменяется задержкой выдачи прав. Награда пригласившему earned по первой успешной основной покупке, применение WAITING до его активного entitlement; не давать награду deviceaddon/повтору. Trial reward earned атомарно с первым eligible trial10; два устройства не дают20дней или двойные7.

## 5. Два конкретных ограничения, которые нельзя скрыть

**Canceled не равен доказанно не оплачиваемый.** payments.record_webhook:877–905 иreconcile:975+ принимают поздний succeeded даже после canceled (`status <> succeeded`). Поэтому освобождать account reservation просто по текущему canceled/expiry нельзя: два discounted provider invoices затем оба могут оплатиться. Безопасный контракт: canceled не consumed, но reservation остаётся RECONCILING до доказанного provider terminal nonpayable; in_flight/unknown никогда не освобождать поTTL. Если provider гарантии/штатной cancellation операции нет, текущий core не может одновременно гарантировать немедленное повторное использование скидки и отсутствие двух оплачиваемых скидочных счетов. Root должен выбрать технический подтверждённый provider cancellation/status путь до runtime; это не новый размер/срок скидки. Не отвергать законную позднюю оплату и не менять её entitlement ради освобождения резерва. Состояние показать «Проверяем закрытие предыдущего счёта», retry/status original order.

**Цена MAIN≤100₽.** Owner утвердил100₽, но current TEST цены10/20₽ и positive-order/provider pipeline не поддерживают ноль/отрицательный итог. Не выбрать молча min100, floor1₽ или платёжную бесплатную активацию. Минимальная реализация: feature refuses discounted quote `409 REFERRAL_PRICE_UNSUPPORTED`, безprovider/consumption, пока root не задаст TEST tariff>100₽ для скидочных fixtures. Если реальные выпускаемые MAIN цены могут быть≤100₽, нужен ровно этот бизнес-выбор владельца; иначе это только TEST config constraint. Старые10₽ счета сохраняются без скидки и переоценки.
