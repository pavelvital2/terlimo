# Referral identity staging and rollback

SOURCE only. No production migration/import or TEST installation performed by this package.

Migration 0038 is additive. All existing accounts become history_pending. A newly inserted local Telegram account also stays history_pending: absence from this database never proves absence of legacy trial/paid/referral history. Normal registration without a candidate still works with its previous wire and creates no benefits automatically.

`referral.stage_history` is an operator-only insert-only import primitive (no API endpoint). It requires exact per-Telegram proof fields and the SHA256 of the accepted protected reconciliation manifest. `proven_new=true` must come from complete accepted legacy coverage/cutover evidence, never from local account INSERT. Imported records preserve stored case-sensitive alphanumeric code and existing first inviter via unique verified accounts.telegram_id. Missing inviter mapping or missing code keeps history pending; ownership conflicts raise/review, never overwrite. Immutable trial_used/first_main_paid flags prevent reissuing historical benefits. Imported referral attribution gets one durable UUID receipt. Repeated exact staging is harmless; changed proof is rejected.

Before staging redeemed legacy histories, the sole operator must reconcile original trial/paid rewards (including WAITING/APPLIED and exact source/target receipts) into referral_rewards. The staging helper does not scrape production, infer missing history, or invent reward ledger records. Stop old parallel award writer as part of a separately authorized cutover. Preserve account mapping, source entitlement/order ownership and applied target revision. This package neither authorizes nor performs that cutover.

Code lookup is exact and case sensitive, preserving the actual stored spelling; input accepts 1–32 ASCII alphanumeric characters. No URL/start-token/Telegram-ID credential parsing. Legacy normalization beyond this policy requires accepted legacy evidence; numeric code lookup is a stored code lookup, never identity proof.

Lock order for candidate/registration: existing bind-account advisory (if known), then installation row, registration rows, candidate rows/account row. Registration initializes account row before benefit row, compatible with payment account KEY SHARE before benefit reservation. New account concurrent appearance uses existing retryable REVISION_CONFLICT rather than acquiring an existing advisory lock under installation. Candidate mutations use installation row only. Payment paths keep their established order and independent referral-discount advisory/benefit lock; no provider I/O in a transaction. Protected staging is offline under sole-writer cutover, not concurrent with these writers.

Candidate mutation keys persist exact raw body digests and definitive 400/404 result before emitted ApiError; changed body conflicts even if malformed. History/storage uncertainty is retryable and has no terminal rejection receipt. Keyed registration stores candidate/token/registration/K immutably; ordinary unkeyed pending requests cannot rotate it. Terminal expired state commits before 410 with original correlation. Confirmation failures leave candidate and original registration replayable. Full terminal receipt includes owner account/candidate/registration/K and fresh confirmed verified Telegram owner and absence of an active foreign binding protect replay; a durable full-slot no_binding proof remains replayable to its original installation/K.

Application rollback retains schema and durable receipt/history rows. The down migration refuses used identities, candidates, staging, benefits or rewards. Do not drop accepted codes/history to simulate a fresh account. No secrets or legacy personal records belong in SOURCE fixtures/reports.
