## Closed wire

All v3 requests: integer `version:3`, operation, `external_key` (old subscription_id pattern), canonical lowercase UUID text `grant_id`, `fence_id`. UUID must match deterministic key; no additional fields.

* Claim adds `operation_id` UUID, `revision` nonnegative int64, `expected_state` absent|active|inactive, `expected_expires_at` UTC whole-second ISO text or null. Absent requires null; existing active/inactive requires exact actual expiry. Claim checks unique marker, details, configured hashes, state/expiry; mismatch writes nothing. It stores the explicit fence/base revision but NEVER creates, extends or activates access. No auto-adopt. New target only on observed absence. Caller must administratively establish that legacy/admin writers are quiescent before adopting; this slice does not perform that transfer.
* Apply adds `operation_id` UUID, `revision` nonnegative int64, `expected_revision` nonnegative int64, `desired_state` active|inactive, `expires_at` UTC whole-second ISO text or null. Active requires a fixed future absolute date for NEW operation; inactive null retains the exact captured base expiry. Inactive explicit expiry sets that absolute expiry. No now+days/max-only business rule. Expected revision must equal accepted; new revision must be greater, not necessarily consecutive. Changed same-operation body rejects, including alternate textual representation of a timestamp.
* Read adds no fields, performs only journal/admin readback. It returns the latest target operation metadata. Foreign fence/not claimed refuses.

Response metadata: version3,status ok,external_key,grant_id,fence_id,accepted_revision,current_revision,current,delivery_state pending|applied|conflict,code,receipt,operation_id,body_digest,desired,artifact. `current` is `{state:absent|active|inactive,expires_at:<integer epoch or null>}` or null when unavailable; current_revision is only the confirmed applied revision if actual current state matches it. Natural expiry of an already confirmed active revision preserves its identity and reads inactive. Broken/wrong hashes/duplicate marker never prove delivery. Desired/applied metadata uses normalized active/inactive/absent and exact epoch; inactive means confirmed non-active record, not deletion. Receipt contains operation_id,digest,external_key,grant_id,fence_id,revision,desired,applied. Claim's absent receipt is adoption evidence only, never an issued grant. Receipt is immutable, separately from CURRENT target/revision; replay of a historical active receipt cannot reactivate or issue commands.

`artifact` is a string produced only from authoritative current details with matching marker/hash/active state/expiry, over the existing protected Unix response. It is empty for inactive/unavailable/unconfirmed current state. Artifact/password is never stored in SQLite or saved evidence. Provided wire fixture deliberately excludes this secret field and describes its required type. Metadata is WDTT direct admin readback, NOT mobile `runtime_applied`, node/SPKI proof, inviter reward or working-VPN claim.

Errors after authorized v3 parsing: `{version:3,status:error,code}`. Stable codes: request_invalid, target_identity_conflict, v3_disabled, journal_unavailable, target_not_claimed, target_claimed, base_mismatch, operation_conflict, operation_pending, revision_conflict, target_readback_conflict, expiry_elapsed plus existing admin error codes. Pre-parse peer/framing errors retain old version1 error envelope. Pending metadata code may be wdtt_unavailable/wdtt_readback_failed/admin_completion_unknown; conflicts include target_readback_conflict/expiry_elapsed/absent_inactive_unsupported. No admin writes on revision/body/claim mismatch or blocked successor.

## Durable ordering and recovery

The same process mutation Lock covers v1/v2/v3 real admin operations and claimed v1 deny. v1 get remains read-only; unclaimed v1 and existing v2 client_test routing remain. SQLite transactions are short FULL-synchronous commits; never span admin I/O. Two tiny tables store target fence/revisions/base plus operation ID/digest/desired/step/receipt; no secret artifacts or passwords. Intent+accepted revision commit atomically BEFORE mutation, then each admin step marks issued BEFORE call and acked AFTER synchronous success, and final exact readback commits receipt+applied revision atomically. No successful adminACK alone counts as applied.

Restart after saved intent BEFORE any issued step reuses exact base/desired; acknowledged partial steps may converge only through the original operation and base/desired intermediate states. Restart after acknowledged remote mutation BEFORE final receipt reconciles exact desired readback without fresh dates or second intent. A successor is blocked while any pending/conflict original remains. Wrong marker/base/expiry/state is a conflict, not silent repair.

**Explicit protocol limits:** the actual admin interface has no operation-status query/CAS/revision fence. If a mutating command has no durable acknowledged completion (uncertain transport, or crash after issued marker but before ack commit), even a desired readback cannot prove that an outstanding old command will never complete later. This implementation honestly retains `pending/admin_completion_unknown`, does not retry that admin mutation or permit a successor; administrative completion proof/recovery remains unresolved by this protocol. It does NOT manufacture a receipt to unblock canonical delivery. The offline partial-success/uncertain fixture proves that boundary. Acknowledged successful receipt after deadline is historical only and never triggers ensure/reactivate.

Also create only exposes an active initial record in this actual admin protocol. Applying inactive to a claimed absent target would briefly issue access before disable; it is therefore `conflict/absent_inactive_unsupported`, with no admin write. No fake successful inactive grant or new endpoint invented.

Fencing guarantees cover requests through this adapter and this journal. Arbitrary direct privileged admin access or a different administrative state directory cannot be revision fenced by this protocol; external writer cutover is a prerequisite and is not claimed complete. No production/runtime success claim.

### A1 response parsing correction

An exception never advances an issued command to acked merely because its generic `uncertain` flag is false. Only normal synchronous success advances that step. Empty, malformed, truncated, oversized, bad-UTF8, duplicate-key, missing-ok and invalid-schema replies after a possible send remain issued. Reopening the journal and replaying even an exact desired readback produces pending/admin_completion_unknown, no receipt or second write, and blocks successors. No typed definitive-negative completion marker is added; v1/v2 admin error semantics remain unchanged.

Affected offline verification adds nine real WDTTAdminClient parser cases using an in-memory socket transport; the successful ACK/crash-before-receipt recovery case is checked alongside them. The original 25-case evidence is retained and is not rerun for A1.

### J1 saved intent after natural BASE expiry

Recovery admits the existing exact `_snapshot_matches(current, base)` natural-expiry condition alongside base/desired intermediate states. With an unissued saved intent and a still-future desired expiry, inactive BASE at the exact old expiry may converge through ordinary set-expiry/activate and exact final readback, completing the same operation/body/revision. The issued gate remains before this check; foreign expiry and elapsed desired expiry remain refused. Three affected temporary-SQLite restart cases cover natural BASE expiry, foreign expiry, and issued-without-ACK; accepted suites are not repeated.
